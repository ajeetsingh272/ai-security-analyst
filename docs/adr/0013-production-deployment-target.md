# ADR-0013: Production deployment target — AWS ap-south-1, EKS, managed Postgres, self-hosted ClickHouse/Redpanda

- **Status:** Accepted
- **Date:** 2026-10-09
- **Phase:** P7
- **Supersedes / Superseded by:** Resolves the open question ADR-0008 §"Bad" explicitly left
  unanswered ("Which real cloud KMS a production deployment uses is a separate, not-yet-made
  decision") and the implicit cloud target `db/clickhouse/0001_events.sql`'s own "Production
  tiering" comment assumed (`s3.ap-south-1.amazonaws.com`) without ever writing it down as a
  decision. Does not supersede ADR-0003 (self-hosted Redpanda, not MSK) or ADR-0005
  (self-hosted ClickHouse, not ClickHouse Cloud) — both stand unchanged; this ADR picks the
  infrastructure those two already-accepted decisions run on top of.

## Context

P7-06: everything that has run in Docker Compose for six phases now needs to run as real,
reproducible production infrastructure. That requires an actual answer to three questions
this repo has so far only hinted at or explicitly deferred:

1. **Which cloud, which region?** No ADR states this. The only concrete textual evidence
   anywhere in the repo is incidental: `packages/billing`'s own storage-pricing comments
   name S3 Standard and EBS gp3 by name, `db/clickhouse/0001_events.sql`'s "Production
   tiering" comment hardcodes `s3.ap-south-1.amazonaws.com`, and the dev stack's own
   `s3-init` service sets `AWS_DEFAULT_REGION: ap-south-1`. Every dollar figure in this
   codebase (`docs/superpowers/specs/2026-10-02-ai-security-analyst-design.md`'s own
   constraint C1: "₹1,800/tenant/month... ₹4,000–30,000 revenue") is in INR, and India is
   this product's named market. Nothing has ever written "we deploy to AWS ap-south-1" as an
   actual decision — until now.
2. **Which managed services, which self-hosted?** ADR-0003 already decided self-hosted
   Redpanda over MSK. ADR-0005 already decided self-hosted ClickHouse over ClickHouse Cloud.
   Neither ADR says anything about the CONTROL-PLANE Postgres, which is a completely
   different, uncontroversial question (RDS vs. self-hosted Postgres is an operational
   choice, not the kind of cost-model trade-off either of those ADRs was actually resolving).
3. **Which secrets manager, which KMS?** ADR-0008 built the `KeyManagementService` seam
   specifically so this question could be answered later without touching anything above
   it. It is later.

## Decision

**Cloud and region: AWS, `ap-south-1` (Mumbai).** Matches every existing cost assumption and
the dev stack's own region env var exactly — this is formalizing an assumption already
baked into comments and pricing tables, not introducing a new one.

**Compute: Amazon EKS**, 3 AZs, managed node groups (not self-managed EC2 + kubeadm) — the
1-to-3-engineer operating team ADR-0003 already named cannot also carry control-plane
operations.

**Control-plane database: Amazon RDS for Postgres 16**, Multi-AZ, automated backups,
encrypted at rest. This is NOT a reversal of ADR-0005 — that ADR chose ClickHouse over an
OLTP store for the EVENT data specifically; it says nothing about whether the control-plane
Postgres itself should be self-managed. RDS is the ordinary, uncontroversial choice for a
transactional database a 1-to-3-engineer team does not want to patch and fail over by hand.

**Event store: self-hosted ClickHouse on EKS** (StatefulSet, EBS gp3 volumes for the hot
tier), exactly as ADR-0005 decided — not ClickHouse Cloud. Cold tier: a real S3 bucket
(`sentinel-cold`, matching the dev stack's SeaweedFS stand-in bucket name exactly), wired via
the storage policy P7-05's own migration already applies; this ADR provisions the bucket and
IAM, P7-05 owns the ClickHouse-side storage policy SQL.

**Stream: self-hosted Redpanda on EKS** (StatefulSet, local-attached storage where the node
group supports it), exactly as ADR-0003 decided — not MSK.

**Secrets and envelope encryption: AWS Secrets Manager + AWS KMS**, filling the exact two
seams already built for this:
- `KeyManagementService` (`packages/db/src/crypto/kms.ts`, mirrored per-connector in
  `go/sentinelconnector/{aws,azure,google,m365}/kms.go`) gets its first real implementation,
  backed by a customer-managed AWS KMS key — `LocalKMS` remains the dev/test implementation,
  unchanged.
- Every other credential (RDS password, ClickHouse admin password, Redpanda SASL
  credentials, connector OAuth client secrets) is generated by Terraform into AWS Secrets
  Manager, never into a committed env file — synced into the cluster as native Kubernetes
  `Secret` objects by the External Secrets Operator (a cluster add-on, itself declared in
  Terraform via `helm_release`), so application code reads an ordinary env var or mounted
  file and never talks to AWS's own Secrets Manager API directly.

**Autoscaling against real signal, not CPU.** The Horizontal Pod Autoscaler for
`detect`/`correlate`/`ingest` scales on Kafka consumer-group lag (via the Prometheus Adapter,
reading the exact `*.consumer_lag` metrics these services already export — `detect.consumer_lag`
is literally already an OpenTelemetry gauge in `services/detect/cmd/detect/main.go`). CPU
alone cannot see a worker that is idling while its own partition backs up; lag can.

**What Terraform owns vs. what plain Kubernetes manifests own.** Terraform owns everything
AC1 means by "infrastructure": the VPC, the EKS cluster and node groups, RDS, S3 buckets, IAM,
Secrets Manager entries, the KMS key, and every CLUSTER ADD-ON (metrics-server, the
Prometheus Adapter, External Secrets Operator, the Redpanda/ClickHouse/Valkey Helm releases)
— all of it `helm_release`/cloud-provider resources, applied by `terraform apply`, never a
console click. `infra/k8s/` owns the seven Sentinel APPLICATION workloads themselves
(`ingest`, `detect`, `correlate`, `eventwriter`, `api`, `dashboard`, `analyst`) as plain
Kubernetes manifests — Deployments, Services, HPAs, ExternalSecrets — deployed by CI, not by
Terraform, because an application deploy (a new image tag) happens far more often than an
infrastructure change and should not need a Terraform run to ship.

## Alternatives considered

### A: GCP (GKE) or Azure (AKS) instead of AWS

Both are perfectly capable. Rejected because AWS is the ONLY cloud with any existing textual
commitment anywhere in this repo (the `ap-south-1` region env var, the S3/EBS pricing
assumptions) — choosing a different cloud now would silently invalidate every dollar figure
`packages/billing` already states as fact, for no offsetting benefit.

### B: A managed Kafka/ClickHouse (MSK, ClickHouse Cloud) instead of self-hosting both

Already rejected, twice, by ADR-0003 and ADR-0005 respectively, for reasons unrelated to
which cloud eventually hosts the self-managed alternative. Revisiting either here would be
re-litigating a decision this ticket was never asked to reopen.

### C: HashiCorp Vault instead of AWS Secrets Manager

Vault is cloud-agnostic and arguably the more "correct" secrets manager for a team that might
ever run multi-cloud. Rejected for now on the same operational-burden grounds ADR-0003 used
against self-managed Kafka brokers: Vault is another stateful service a 1-to-3-engineer team
would have to run, unseal, and back up, when AWS Secrets Manager is already paid for by
virtue of being on AWS at all and needs none of that.

### D: A single-AZ, single-node-group cluster to save cost

Rejected: constraint C1 is about PER-TENANT cost of goods, not about skipping the baseline
availability a 10,000-tenant multi-tenant platform owes every tenant sharing it. A single-AZ
failure taking down every tenant at once is a far larger business risk than the marginal cost
of a second and third AZ.

## Consequences

### Good

- Every cost figure already written down elsewhere in this repo (storage pricing, the ₹1,800
  COGS target) now has a real infrastructure target consistent with it, rather than resting
  on an assumption nothing ever confirmed
- The `KeyManagementService`/envelope-encryption seam ADR-0008 built specifically for this
  moment gets used exactly as designed, with zero changes above it
- Autoscaling on consumer lag catches the exact failure mode CPU-based autoscaling is blind
  to: a backed-up partition behind an idling worker
- Terraform/K8s split means an application deploy never requires touching infrastructure code

### Bad

- AWS ap-south-1 lock-in: a future multi-cloud or different-region requirement (P7-11,
  cuttable) means real migration work, not a config flag
- Running EKS, RDS, self-hosted ClickHouse AND self-hosted Redpanda simultaneously is four
  different operational surfaces for a 1-to-3-engineer team, even with managed compute
- External Secrets Operator is one more cluster add-on and one more thing that can fail
  between "Secrets Manager has the value" and "the pod can read it"
- This ADR's own IaC could not be proven against a REAL AWS account in the environment it
  was authored in (no cloud credentials available) — `terraform validate`/`fmt` and
  `kubectl --dry-run=client` are real, local checks; `terraform apply`, a real pod-failure
  drill, a real autoscaling-under-load test, and a real timed rebuild are not, and are
  disclosed as such rather than claimed

### Risks and how they are mitigated

| Risk | Mitigation | Owner |
|---|---|---|
| EKS control-plane or node-group misconfiguration only surfaces at real `apply` time, never caught by `validate` | A staging AWS account should run `terraform apply` before any production run — out of this ADR's own ability to prove, named explicitly rather than silently assumed fine | Platform |
| Consumer-lag-based HPA has no real load-test evidence in this environment | P7-07's own load test is the real proving ground, disclosed there as partial for the same no-real-cloud reason | Platform |
| Secrets Manager / External Secrets Operator outage blocks new pod scheduling | Existing pods keep their already-mounted secrets (Kubernetes does not re-fetch on every restart); documented as a known dependency, not eliminated | Platform |

## Revisit when

A real AWS account exists to run `terraform apply` against, or a contractual data-residency
requirement forces a different region/cloud entirely (P7-11's own trigger).
