# ADR-0009: Hand-written SQL owns the schema; the typed layer is generated from it

- **Status:** Accepted
- **Date:** 2026-10-02
- **Deciders:** Pratik Soni
- **Phase:** P0
- **Supersedes / Superseded by:** —

## Context

ADR-0005 put the control plane in Postgres, and ADR-0008 made tenant isolation a
property of the database rather than of the application. That second decision is what
forces this one.

The isolation in `0001_foundation.sql` is not expressible as table shape. It is:

- `ALTER TABLE ... FORCE ROW LEVEL SECURITY` — without FORCE, the table owner silently
  bypasses every policy, and the control becomes decoration;
- a `tenant_isolation` policy per table, whose `USING` expression reads
  `current_setting('app.tenant_id')`;
- `CREATE ROLE sentinel_app ... NOBYPASSRLS`, where the absence of one keyword is the
  entire guarantee;
- `REVOKE UPDATE, DELETE ON audit_log` plus two triggers that raise on either, which is
  trust guarantee TG6;
- a composite foreign key on `connector_cursors (connector_id, tenant_id)` that makes a
  cursor disagreeing with its connector unrepresentable.

Every item on that list is a security control, and five of the six cannot be generated by
`drizzle-kit` from TypeScript definitions today. Meanwhile the product plane is
TypeScript and genuinely needs types for these tables, and hand-written types drift from
the database the moment someone is in a hurry.

So the question is narrow: which artefact is the source of truth, and which is derived?

## Decision

**The SQL under `db/postgres/migrations` is the source of truth.** It is applied by
`scripts/migrate.sh`, which tracks a `schema_migrations` ledger with a checksum per file
and refuses a migration edited after it was applied. To change the schema, write a new
migration.

**`packages/db/src/schema.ts` is generated from the live database** by `pnpm db:pull`
(`drizzle-kit pull`, then `scripts/postprocess.mjs`). It is marked generated, excluded
from linting, and overwritten on every pull. Drizzle is a typed query builder here and
nothing more.

Generation runs one way only. `drizzle-kit generate` and `drizzle-kit push` are **not to
be run against this schema**: both treat `schema.ts` as authoritative and would emit a
schema missing every policy, trigger, grant and role above — silently, and in a form that
looks complete.

Two derived artefacts keep the arrangement honest, both gated in CI:

- `docs/architecture/data-model.md` is generated by introspection and `pnpm db:docs:check`
  fails if it is stale, so the document describing the isolation posture cannot drift from
  the database it describes.
- `pnpm db:validate` enumerates tables from the live database and fails if any outside an
  explicit, reasoned allowlist lacks a non-null `tenant_id`.

## Alternatives considered

### A: Drizzle Kit owns migrations, generated from `schema.ts`

Attractive because it is the mainstream Drizzle workflow, gives one place to edit, and
makes the types definitionally correct rather than correct-by-regeneration.

It lost on the security surface. The policies, FORCE flags, grants, role attributes and
immutability triggers would have had to live in hand-written custom SQL steps *anyway*,
so ownership would be split: table shape in TypeScript, every control in SQL. Split
ownership of one schema is worse than single ownership of either, because a reviewer
reading one file cannot tell what the other does. It would also have meant rewriting a
migration that already passes twenty isolation and audit assertions, to gain nothing the
generated path provides.

### B: No Drizzle; hand-written types over `pg`

Fewest moving parts, no generator, no post-processing step. Rejected because hand-written
types *are* the drift problem. A type that says `tenant_id: string` when the column became
nullable is a lie the compiler enforces, and it would be discovered in production.

### C: Generate the SQL from an ORM-agnostic schema DSL

Rejected as a third representation of the same thing. The reviewability of the isolation
rules is the property being protected, and plain SQL in a diff is the most reviewable form
available.

## Consequences

### Good

- Every security control is plain SQL in a reviewable diff, and a reviewer needs no
  knowledge of a generator's capabilities to judge whether isolation holds.
- The TypeScript types cannot contradict the database, because they are read out of it.
- Migrations are immutable once applied, enforced by checksum rather than by convention.
- The generated data-model document means the isolation posture can be checked without
  opening `psql`, and CI fails if that document goes stale.

### Bad

- Two commands instead of one: a schema change is a migration *and* a `pnpm db:pull`. Forget
  the second and the types are stale — caught at compile time, but still friction.
- The schema layer needs `scripts/postprocess.mjs`, because `drizzle-kit pull` emits
  `unknown()` placeholders for `bytea` and `citext`. That is a small amount of bespoke
  tooling to maintain.
- `drizzle-kit pull` exits 0 even when it fails, so its exit code is not a usable gate and
  the post-processor has to assert on the output instead.
- Contributors who know Drizzle will reach for `generate` or `push` out of habit. The
  config file says not to, but a comment is not a guardrail.

### Risks and how they are mitigated

| Risk | Mitigation | Owner |
|---|---|---|
| Someone runs `drizzle-kit push` and drops every policy | Documented prominently in `packages/db/drizzle.config.ts` and `docs/getting-started.md`; `pnpm verify` asserts FORCE RLS and the audit grants, so the damage fails CI rather than shipping | P0-05 |
| `schema.ts` goes stale after a migration | `pnpm typecheck` catches a removed column; a drift check comparing a fresh pull against the committed file is not yet automated | P0-05 |
| A new column type yields an `unknown()` placeholder | `scripts/postprocess.mjs` exits non-zero on any unmapped type and names it, rather than emitting a file that does not compile | — |
| The data-model document drifts | `pnpm db:docs:check` in the CI integration job | — |
| A new table is added with no tenant | `pnpm db:validate` treats every table as tenant-scoped unless allowlisted with a written reason | P0-05 |

## Revisit when

`drizzle-kit` can generate `FORCE ROW LEVEL SECURITY`, per-table policies, role attributes
including `NOBYPASSRLS`, and column-level `REVOKE` — all four, verifiably, in a released
version. At that point option A becomes a real choice rather than a split, and the
duplication this ADR accepts is no longer buying anything.
