# Progress Dashboard

A single page showing phase completion, ticket status, test-case coverage and
the trust-guarantee scoreboard. Generated by `tools/progress/build.mjs` from two
sources: `planning/` (the plan) and the GitHub issues API (reality).

```bash
node tools/progress/build.mjs            # anonymous; works, but rate-limited
GITHUB_TOKEN=$(gh auth token) node tools/progress/build.mjs   # authenticated
```

Outputs into `site/`:

| File | Purpose |
|---|---|
| `index.html` | Standalone page for GitHub Pages |
| `artifact.html` | Same page as a Claude Artifact fragment (no document skeleton) |
| `progress.json` | Machine-readable snapshot for any other consumer |

Both HTML variants are composed from one `STYLE` and one `BODY` string, so the
hosted copy cannot drift from the Pages copy.

If the GitHub API is unreachable the page still builds from `planning/` alone and
says so on the page, rather than failing the deploy and leaving a stale page with
no explanation.

## Hosting

`.github/workflows/progress.yml` rebuilds and deploys on every issue event, on
pushes to `planning/`, daily at 03:00 UTC, and on manual dispatch.

**It will not deploy yet.** GitHub Pages is unavailable for private repositories
on the GitHub Free plan — enabling it returns:

```
422: Your current plan does not support GitHub Pages for this repository.
```

The workflow is correct and committed; it starts working the moment one of these
is true. Three options, in the order most projects should consider them:

### 1 · Upgrade to GitHub Pro — recommended

Roughly $4/month. Pages on private repositories, plus required reviewers on
protected branches. Nothing in this repository changes; the workflow begins
deploying on its next run.

```bash
# after upgrading
gh api repos/ajeetsingh272/ai-security-analyst/pages -X POST -f build_type=workflow
```

### 2 · Make the repository public

Pages is free for public repositories. Consider what that publishes: this
repository contains the pricing model, cost of goods, go-to-market plan and
pilot targets. The architecture is defensible in the open; the commercial plan
is the part to think about.

### 3 · Keep using the hosted Artifact

`site/artifact.html` is published as a private Claude Artifact, which is where
the dashboard currently lives. It is not rebuilt automatically — refresh it by
regenerating and re-publishing when you want it current. Good enough for sharing
a snapshot with someone who does not have repository access; not a substitute
for the automated page.

## How status is derived

| Shown as | Condition |
|---|---|
| Done | Issue closed |
| Blocked | A label containing "blocked" |
| In Review | A label containing "in review" |
| In Progress | A label containing "in progress", or any assignee |
| Ready | Open issue, no assignee, no status label |
| Backlog | No matching issue found for the ticket id |

"Ready to start" lists unblocked tickets — every dependency closed — ordered by
priority. That list is the answer to "what should I pick up next", and it is
computed rather than curated, so it cannot go stale.
